Architecture

i What this is

WhatThe connection map: identity sources, AWS, the edge, the hubs, the workload clusters and storage.

WhyTwo constraints shaped this. Hardware was scarce — a third of the GPUs failed before the build started — so rather than spend three machines on a control plane per cluster, every workload cluster's control plane runs as pods on a shared hub. And the identity provider sits outside the data centre, because the thing that lets you log in must not depend on the thing you log in to fix. The diagram exists to make both visible at once.

Look forBoxes marked NO LINKS IN SOURCES — real components whose connections nothing records, drawn unconnected rather than wired up by guesswork. Also any ?, and the absence of control-plane nodes on the workload clusters: that absence is the architecture working.

Clusters

i What this is

WhatEach cluster as declared in Git — node pools, components, tenant projects, isolation tiers, VLANs and machines.

WhyUnder hosted control planes a workload cluster owns only worker nodes. Its API server, etcd and scheduler are pods in a clusters-<name> namespace on its hub, which is why a workload cluster's size is a node-pool count and its control plane appears in the hub's namespace list instead. Hubs are ordinary clusters and do have their own nodes, but they are installed by a different route and so are declared in a different repository.

Look forGPU counts marked needs data; the source line under a hub's node count; and whether the node-pool replicas in oac-apps agree with the machine inventory — two independent sources counting the same thing.

Discoveries

i What this is

WhatDefects and surprises found during the build, with current status, each citing an issue.

WhyThe expensive failures were consequences of the architecture rather than faults in it. Consolidating control planes onto hubs moved the scheduler out of the workload cluster — and took the metric the invoices are built from with it. Keeping these listed is what stops a decision's cost from being forgotten once the decision looks settled.

Look forAnything still Open, especially serious or critical, and whether a fix created its own follow-on problem.

Tenant projects

i What this is

WhatEvery tenant project across all clusters: who asked for it, what it is for, which groups hold edit on it, and the quota it runs under.

WhyA project is the unit of tenancy — it is a namespace, a quota, a limit range, a network policy and a set of RoleBindings created together by the user-projects chart from one entry in a values file. Because that entry is in Git, who requested a project and why is recorded rather than remembered, which is also what makes the tenancy auditable.

Look forProjects whose quota is not the chart default, and the difference between the production clusters, where projects are tracked in a values file, and development, where they are created more loosely.

Identity

From moc-keycloak.

i What this is

WhatRealm settings, federated providers, per-cluster OIDC clients, groups and authentication flows, read from the Terraform.

WhyMOC serves users from many institutions it does not control, so it federates rather than holding passwords. But federation alone would let anyone with a valid university account in, so the first-broker flow links only accounts that already exist — the platform refuses unknown users by construction rather than by policy document. The realm flags are that intent expressed as configuration.

Look forClients marked no cluster — a cluster being prepared before its configuration exists. Values shown as variable, which the repository alone cannot resolve. And the realm flags: registration disabled, email login disabled, duplicate emails disallowed.

Realm

i

WhatThe Keycloak realm’s security-relevant settings.

WhyThese flags are the access policy expressed as configuration rather than as a document: registration disabled, email login disabled, duplicate emails disallowed. A policy written only in prose cannot be checked; these can.

Look forAny flag set true where you expected false, and the token and session lifespans.

Identity providers

i

WhatThe federated providers configured on the realm.

WhyFederating is how a platform serves users from institutions it does not control without ever holding their passwords — the home institution authenticates, MOC receives an assertion.

Look forSync mode, whether email is trusted, and which first-broker flow each provider runs. That flow is what decides whether an unknown user can be created.

Authentication flows

i

WhatEach flow and its executions, in order, with the requirement level.

WhyThe order and the requirement level are the login policy. Require Existing User First Broker Login detects an existing account and links it, with no step that creates one — which is how “only pre-registered users may log in” is enforced mechanically rather than by policy document.

Look forREQUIRED steps, and whether any flow contains a step that would create a user it has not seen before.

Hardware

i What this is

WhatEvery machine listed in the open-accelerator-infra hardware document, with the VLANs its NICs carry, its BMC address, and whether a cluster currently claims it.

WhyThe cluster views only show machines that belong to a cluster, which is a minority of the fleet. The rest is the capacity question: how much idle hardware exists, how much is broken, and how much is being held for the RHOSO 18 build. A platform assembled from decommissioned hardware is defined as much by what is unusable as by what is running.

Look forMachines flagged flagged (boot failures, unreachable BMCs, disk faults) and those reserved for RHOSO 18. Note the document records its own unknowns — three R440s are listed as ?? R440-1 ?? and are skipped here.

Networks

i What this is

WhatVLANs and switch ports from ansible-switches, joined to CIDRs from the hardware document and Terraform.

WhyA pod is attached only to the cluster network, but the storage array serves NFS and S3 on a separate, faster VLAN. That single fact forces a second network interface on every node, a proxy for object storage, and wider storage subnets — so the physical VLAN table is where an apparently abstract Kubernetes problem becomes a cabling one.

Look forVLANs carrying real ports but claimed by no declared cluster — including the MOCSEC-* set, which is the NIST environment already wired at the network layer. Also whether a storage VLAN's CIDR matches what Portworx declares; the two are maintained in different repositories.

VLANs with no declared cluster

i

WhatVLANs carrying configured switch ports that no cluster in oac-apps claims.

WhyPhysical provisioning runs ahead of cluster configuration — ports and VLANs are cut over before the Git config that uses them exists. So this list is a preview of what is being built next, visible before any cluster declares it.

Look forThe MOCSEC-* set, which is the NIST/HIPAA environment already wired at the network layer, and the OAC staging and dev-workload1 networks.

Switches

i

WhatEvery switch in the ansible-switches inventory, with its management address, network OS and fabric.

WhySwitch configuration is managed as code in the same way cluster configuration is, so the inventory is the authoritative list of what the VLAN assignments are applied to. The fabric column is what decides which VLANs may exist on a switch.

Look forThe mocsecdata and mocsecmgmt fabrics, which belong to the NIST environment rather than to OAC.

Capacity

i What this is

WhatNode pools each workload cluster declares, and the GPU count that implies.

WhyGPUs are the scarce resource and billing is by reservation rather than use, so declared capacity is the number that generates an invoice. The metric that would show real utilisation is unavailable under hosted control planes, so this section deliberately reports what was reserved and says why the other half is missing.

Look forSegments whose GPU count is unknown, and the note on the missing billing metric — the gap between reserved and used is the open policy question, and it currently cannot be measured.

Charts

i What this is

WhatEvery Helm chart in oac-apps and which clusters it deploys to.

WhyThere is no ordering between components. Each chart is an independent Argo CD Application that syncs in parallel, fails if its dependencies do not exist yet, and retries until they do. So where a chart lands is decided by an ACM placement label on the cluster, not by a position in a sequence — which is why the useful question is "which clusters match" rather than "what runs first".

Look forCharts marked not referenced: present in the repository but named by no ApplicationSet, so nothing deploys them.
